# Ariadna: matriz de trazabilidad

Estado: actualizada el 11 de noviembre de 2026. ARD-10 a ARD-21 tienen incrementos de implementación publicados. ARD-22 tiene el ciclo de instalación, inicio y desinstalación verificado, pero su ejecución más reciente no publicó el artefacto y permanece en revisión. ARD-11 a ARD-15 cuentan con evidencia de aceptación visual parcial; faltan criterios por conciliar. ARD-16 añade diagnósticos locales JSON Lines, ARD-17 amplía las pruebas unitarias de dominio, ARD-18 verifica atomicidad SQLite, ARD-19 aporta controles de seguridad y validación, ARD-20 valida CI sobre Windows y ARD-21 mide rendimiento con datos sintéticos.

## Decisiones técnicas que resuelven pendientes

1. La aplicación es un monolito modular de escritorio con Rust estable y Tauri v2.
2. La interfaz se comunica con la capa de aplicación mediante IPC de Tauri. No se publica una API HTTP, no se abre un puerto de backend y no se integra un WMS, ERP o lector físico.
3. SQLite local con SQLx es la persistencia del prototipo. Las migraciones SQL versionan el esquema.
4. El simulador llama los mismos casos de uso de aplicación que usa la interfaz. El contrato del evento es interno y tipado; no requiere HTTP, MQTT ni un servicio externo.
5. Se usan ubicaciones configuradas manualmente y datos sintéticos. No se afirma que el simulador represente lecturas RFID reales.

Estas decisiones concretan ADR-01 a ADR-07 y DEC-04 a DEC-08. Las versiones 0.2 de Visión y alcance y Requisitos y criterios de aceptación, y la versión 0.9 de Arquitectura y decisiones técnicas registran estas elecciones. ARD-10 define el puente IPC interno; ARD-11 usa ese contrato para mostrar jerarquía y ocupación sin incorporar geometría física ni hardware. Documento AETHER vinculado: Matriz de trazabilidad de requisitos, ID 3a65eb00-0457-4e44-be52-80739fcfc560.

## Estado de evidencia

ARD-14 añade `search_inventory`, `list_alerts` y `mark_alert_reviewed`, mantiene el acceso vía IPC y presenta búsqueda, cronología y alertas. ARD-15 añade `run_simulation`, cinco recorridos sintéticos y la migración que admite vínculo exacto a eventos o intentos. ARD-17 añade pruebas unitarias para límites de productos, jerarquías y datos de ubicación, líneas con lote, estados de unidades, ocupación, eventos, correcciones y alertas. La aceptación visual manual de ARD-11 a ARD-15 continúa pendiente.

ARD-18 añade pruebas de integración para rollback después de una escritura parcial de recepción y cuando falla la inserción de una alerta vinculada a un traslado. ## Evidencia de ARD-21

ARD-21 añade `src-tauri/examples/ard21_benchmark.rs`, un ejecutable reproducible que crea una base SQLite temporal mediante los casos de uso de catálogo, recepción, almacenamiento, traslados y despacho. Genera 500 unidades, 255 ubicaciones totales (252 posiciones), 25 productos y 10.000 movimientos aceptados; valida cantidades exactas, estados, cero intentos rechazados y las cardinalidades de búsqueda e historial antes de medir. Ejecuta 10 calentamientos y 101 muestras por operación en `release`, en tres bases independientes. La búsqueda de `SKU-000` devuelve 21 resultados, el historial de `unit-000000` contiene 20 entradas y el movimiento alterna una unidad entre dos posiciones.

En Windows 11 Pro x64, Intel Core i5-12450H, 8 núcleos/12 hilos, 31,8 GiB de memoria, Rust 1.99.1 y SQLite 3.51.3, la mediana p95 de las tres repeticiones fue: búsqueda 10,057 ms, historial 0,561 ms y movimiento 7,255 ms. Todos los p95 individuales quedaron bajo la meta provisional de 2 s; el mayor p95 observado fue 191,665 ms para movimientos. Los informes automáticos registran la revisión Git `3acb83948047`, compilador y hardware; el método y sus límites están en `docs/performance/ard-21-baseline.md`.

Verificación local: `cargo fmt --check`, Clippy con `-D warnings`, 71 pruebas Rust, tres pruebas del ejemplo y tres ejecuciones del benchmark en `release` pasaron. El run [43083026333](https://github.com/shdez-dev/ariad/actions/runs/43083026333), para `3acb839`, pasó los cuatro grupos frontend, Rust, el ejemplo del benchmark y la compilación Tauri Windows. La prueba no incluye interfaz, serialización IPC, concurrencia ni uso real de bodega. Siguiente tarjeta técnica: ARD-22, preparar y comprobar el instalador de Windows. La aceptación visual manual de ARD-11 a ARD-15 sigue pendiente.

## Trabajo en curso de ARD-22

La rama `feat/ard-22-windows-installer` limita el bundle Windows de Tauri al instalador NSIS. El formato MSI queda fuera de esta etapa. `.github/workflows/ci.yml` construye el instalador y lo conserva junto con el informe de verificación durante 14 días. En un runner hospedado y limpio, `scripts/verify-windows-installer.ps1` ejecuta instalación y desinstalación silenciosas, inicia Ariadna dos veces y confirma un nuevo evento `app.startup`, la base SQLite y el registro bajo `%APPDATA%\com.ariadna.inventory`. El script rechaza runners autoalojados para evitar escribir en perfiles persistentes.

La configuración no contiene certificado ni comando de firma; el instalador local se reportó como `NotSigned`. La guía `docs/distribution/windows-installer.md` explica su generación, ubicaciones locales, advertencias de firma y límites. El run [43088310304](https://github.com/shdez-dev/ariad/actions/runs/43088310304) pasó en Windows para el commit `32e8750e624422a3457e4f4e7237e5a58147aea2`: pasaron las cuatro suites frontend, Clippy, 71 pruebas Rust, tres pruebas del benchmark, el bundle NSIS y el ciclo de instalación, inicio, segundo inicio, base local y desinstalación. Actions conserva el artefacto `ariadna-windows-nsis-32e8750e624422a3457e4f4e7237e5a58147aea2` (ID `13888650880`) con instalador e informe por 14 días. El informe incluye el hash SHA-256 y el resultado de cada verificación. No se instaló el artefacto local sobre el perfil de desarrollo, que ya presentaba un checksum de migración distinto; la verificación automatizada usó un runner hospedado limpio.

El 11-11-2026 se revisaron manualmente el ZIP y el informe del artefacto anterior. El SHA-256 del ZIP descargado coincide con el digest que GitHub publica (`2cc26cef146856c0adf2b3257cd7c739cac5ff52c59eff9f4987fec4a59c133e`). El paquete contiene `Ariadna_0.1.0_x64-setup.exe` (2.375.932 bytes) y `ariadna-ard-22-verification.md`. El SHA-256 del instalador (`A995DC8B674F4F60E55B580130CB036628FA42EFC16615A71B5F2E065CB99E37`) coincide con el informe; `Get-AuthenticodeSignature` devuelve `NotSigned`, sin certificado de firmante. ## Revisión parcial de interfaz y accesibilidad de ARD-11 a ARD-15

El 11-11-2026 se volvió a compilar y abrir la aplicación Tauri con un perfil de demostración aislado. En la vista de mapa se comprobaron la jerarquía sintética de zona, pasillo, rack y posiciones, la ocupación guardada y la actualización de la vista; la interfaz muestra `Pasillo` mediante el catálogo español de niveles. Con teclado se recorrió la navegación y las posiciones, se seleccionó una posición y se comprobó que el detalle cargara su pallet, producto, cantidad y estado; el mensaje de estado anunció la selección. En búsqueda transversal, el control conserva el nombre accesible `Buscar productos, pallets o ubicaciones` después de introducir texto y devuelve el producto y la unidad sintéticos esperados.

Se corrigieron los nombres accesibles de los cuatro filtros de productos, ubicaciones, unidades y búsqueda; se aumentó el tamaño y contraste de textos pequeños en el mapa, las tablas, controles, estados y pie de página; y el mapa dejó de presentar el tipo `aisle` en inglés. La revisión independiente del cambio no encontró regresiones claras. En esta sesión se inspeccionaron flujos de alta, edición, desactivación lógica, duplicados y estado vacío en los catálogos de productos y ubicaciones. Se verificaron mensajes de error para SKU duplicado y etiqueta repetida, el bloqueo del traslado cuando no existe una posición activa libre, y los escenarios deterministas de duplicado, etiqueta desconocida, ubicación inválida y destino ocupado, además del recorrido normal ya observado. Las anomalías verificadas quedaron asociadas al intento esperado y las operaciones inválidas se rechazaron sin confirmar cambios. En sesiones previas se recorrieron recepción, asignación, traslado y despacho, la cronología y la revisión de alertas.

Esta evidencia visual cubre una parte importante de ARD-11 a ARD-15, pero no equivale aún a aceptación completa: falta cotejar criterio por criterio contra las tarjetas, repetir los recorridos afectados en el estado final del candidato, revisar estados de carga/error/vacío de cada vista y conservar evidencia revisable. Las tarjetas siguen en progreso hasta esa conciliación y cualquier criterio pendiente. La inspección usó datos sintéticos en una ventana Tauri con perfil de demostración aislado; no usó hardware ni el perfil local de operación.

Verificación de este incremento: `npm run build`; pruebas frontend `test:map` (3), `test:catalog` (4), `test:simulator` (5), `test:ipc` (2) y `test:accessibility` (2); `cargo test` (71); `cargo fmt --check`; y `cargo clippy --all-targets -- -D warnings`, todos exitosos. El workflow añade `test:accessibility` para proteger los nombres accesibles y las etiquetas españolas de ubicación. La captura/observación fue sobre la ventana Tauri en Windows con datos sintéticos y no usa el perfil local de operación. Mantener ARD-11 a ARD-15 en progreso hasta completar y registrar cada criterio pendiente.
